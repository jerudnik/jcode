# Releasing Jcode

Jcode is an independent hard fork. `main` is the sole product authority and the
immutable `fork-point` tag remains the quality-gate anchor. Repository-owned
end-user distribution is exclusively Nix-based: `flake.nix` defines the package
and the public `jerudnik-jcode` Cachix cache serves trusted build outputs.

GitHub Releases are metadata-only. They contain release notes and source/tag
metadata, never executable archives, checksums, installers, or package-manager
payloads.

## Official fork release name

The first official fork release is `v1.0.0` unless the operator chooses one
explicit fork-prefixed replacement name before tagging. If that product decision
changes, stop before publication and use that one name everywhere: Cargo version,
changelog, tag, release gate, release notes, install test, and rollback record.

Old `v0.*` tags are pre-fork history. Do not use them as release proof, and do
not accept a `v0.*` tag outside authoritative `main` history as evidence that a
fork release was promoted.

## Release prerequisites

- The release commit is on `main` and the worktree is clean.
- The version in the root `Cargo.toml` matches the release tag without the `v`
  prefix. For the default first fork release, that means `version = "1.0.0"`.
- `Cargo.lock` and `flake.lock` are committed and coherent.
- `CHANGELOG.md` documents the candidate release, Nix/Cachix distribution, SBOM,
  provenance, metadata-only GitHub Release, install test, and rollback test.
- User-facing release notes can be generated by `scripts/generate_release_notes.sh`.
- Relevant Rust, policy, workflow, documentation, and Nix gates pass.
- The public Cachix cache and its signing configuration are healthy.
- A previous promoted rollback ref is selected. It must resolve to an ancestor of
  authoritative `main`; it must not be an old detached `v0.*` tag used as fork
  release proof.

## Prepare and validate

1. Create a topic branch from `main` for version, changelog, and release-document
   changes.
2. Run the narrow checks while iterating, then the maintained final gates from
   `docs/agent-workflows.md`.
3. Run the release contract gate before tagging:

   ```bash
   python3 scripts/release_check.py --release v1.0.0 --rollback-ref <previous-promoted-main-ref>
   ```

   Use a different `--release` only if the operator chose a single replacement
   name before tagging.

4. At minimum, validate the package and release evidence:

   ```bash
   system="$(nix eval --raw --impure --expr builtins.currentSystem)"
   nix build --accept-flake-config \
     ".#packages.${system}.jcode" \
     ".#packages.x86_64-linux.jcode-sbom" \
     ".#packages.x86_64-linux.jcode-provenance" \
     --no-link --print-out-paths
   nix run --accept-flake-config .#jcode -- version
   ```

5. Verify the built output is cached, or wait for the main/tag Nix workflow to
   push it before telling users to install it:

   ```bash
   out="$(nix build --accept-flake-config .#packages.${system}.jcode --no-link --print-out-paths)"
   curl --fail --head "https://jerudnik-jcode.cachix.org/$(basename "$out").narinfo"
   ```

6. Merge the release preparation through the normal review path. Do not tag a
   topic branch or an unmerged commit.

## Tag and publish

From an up-to-date, clean `main`:

```bash
git fetch --all --prune
git switch main
git pull --ff-only
python3 scripts/release_check.py --release v1.0.0 --rollback-ref <previous-promoted-main-ref>
git tag -s v1.0.0 -m "Jcode v1.0.0"
git push <fork-remote> v1.0.0
```

Discover the configured fork remote with `git remote -v`; do not assume it is
named `origin`.

A `v*` tag runs `.github/workflows/release.yml`. The workflow verifies that the
tagged commit belongs to authoritative `main`, runs `scripts/release_check.py`
with `--require-tag`, builds or substitutes the Nix package, verifies the SBOM
and provenance outputs, checks Cachix narinfo availability, smoke-tests install
from the tag and rollback ref, renders notes, and publishes a metadata-only
GitHub Release. Publication fails if assets are attached.

The flake and Cachix are the only repository-owned binary authority. Retired
channels must not be recreated, including shell or PowerShell installers,
Homebrew, AUR, GitHub executable assets, checksum manifests for those assets,
the native iOS application, signed app-store/TestFlight delivery, or Cargo
registry publication.

## Verify after tagging

- Confirm the release workflow succeeded for every maintained release system.
- Confirm Cachix serves the tagged package closure.
- Confirm `packages.x86_64-linux.jcode-sbom` contains the SBOM JSON.
- Confirm `packages.x86_64-linux.jcode-provenance` records the exact source
  revision and built package output.
- Run the tagged package through Nix and check its version:

  ```bash
  nix run github:jerudnik/jcode/v1.0.0 --accept-flake-config -- version
  ```

- Confirm the GitHub Release is public, contains the expected notes, and has zero
  assets.
- Confirm `main` and the immutable `fork-point` tag were not moved or rewritten.

## Updating an installation

Updates are owned by the consumer's Nix configuration:

```bash
nix profile upgrade jcode
# or update the pinned flake input, then rebuild the owning configuration
nix flake update jcode
```

`jcode update` and `/update` only print Nix guidance. They never fetch, build,
replace, or mutate the running executable. Explicit self-development rebuilds
remain developer workflows and are not end-user distribution channels.

## Rollback

Rollback means returning the consumer's Nix input to the previous promoted
main-ancestor ref selected before tagging. The rollback ref is passed to
`scripts/release_check.py`, which rejects missing refs and rejects `v0.*` tags as
official fork release proof.

Test rollback before final promotion:

```bash
nix run github:jerudnik/jcode/<previous-promoted-main-ref> --accept-flake-config -- version
```

For pinned consumers, change the flake input back to
`<previous-promoted-main-ref>` and rebuild the owning Nix profile, Home Manager,
NixOS, or nix-darwin configuration. Do not publish a replacement installer or
GitHub binary asset for rollback.
